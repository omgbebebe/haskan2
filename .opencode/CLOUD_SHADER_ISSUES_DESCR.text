Code Review & Architectural Analysis Report: Clouds.hs
Target File: Deferred/Clouds.hs (Haskan2 Vulkan Render Pipeline)
Status: Non-Production Ready (Prototype/Draft)
Executive Summary
The analyzed shader implements a volumetric cloud rendering pass using a Haskell-based SPIR-V DSL (FIR). While the mathematical foundations of density erosion (Schneider-Vollnov method) and phase functions are architecturally correct, the core raymarching execution is fatally flawed.
By flattening the raymarching pipeline into a fixed 6-step unrolled sequence, the shader introduces severe visual artifacts, breaks camera-in-cloud traversal, and forces massive register pressure on the GPU.
Technical Breakdown of Fatal Issues
1. Unrolled 6-Step Fixed Raymarching
The Code: The shader samples density at precisely 6 hardcoded points (p0 through p5) along the view ray.

GPU Impact: Unrolling forced-binds multiple sampler registers concurrently (n0 to n5), spiking register pressure (VGPR usage) instead of reusing a single register across iterations.
2. Fake Light Marching (Single-Sample Shadowing)
The Code: To calculate lighting at each step, the shader offsets the texture lookup vector along the sun direction vector once (sunTexOffsetX/Y/Z) and takes one sample (ln0 to ln5).
The Issue: Real volumetric lighting requires calculating the optical depth from the current ray position all the way to the edge of the cloud volume along the sun ray. Sampling just one neighbor pixel fails to account for self-shadowing deep within thick cloud structures. Beer's Law attenuation becomes mathematically meaningless here.
3. Broken Camera Traversal (No Plane/AABB Intersector)

4. Flawed Temporal Reprojection
The Code: A historical reprojection step blends the current color with a cloud_history texture using the previous frame's View-Projection matrix.
The Issue: Because the shader does not compute or read true Motion Vectors (velocity buffers) for the clouds—which shift dynamically via wind vectors (windX, windZ)—the history lookup projects static world coordinates. Moving clouds will leave massive, ghosting trails across the screen.

Step 2: Implement a Robust Ray-AABB / Dual-Plane Intersector
To allow the camera to move seamlessly from ground level up through the atmosphere, replace the native tEntry math with a standard horizontal slab intersector.
hlsl
// Handles camera being below, inside, or above the volume
float tTop = (cloudTop - camY) / dirY;
float tBottom = (cloudBottom - camY) / dirY;

float tNear = max(0.0, min(tTop, tBottom));
float tFar = max(0.0, max(tTop, tBottom));

if (camY >= cloudBottom && camY <= cloudTop) {
    tNear = 0.0; // Camera is inside clouds; start marching immediately
}

Step 4: Fix Wind Vector Temporal Reprojection
When pulling the history sample from cloud_history, the pixel coordinate lookup must subtract the cumulative wind displacement vector accrued between the previous frame and the current frame. This ensures the historical validation pixel tracks the moving cloud mass instead of the world geometry underneath it.
